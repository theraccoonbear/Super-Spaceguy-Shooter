## High

### 1. The public score endpoint can be flooded or defaced by anyone holding a binary

**Evidence**
- `server/src/index.ts:59-62`: `POST /scores` is gated only by `requireKey`.
- The key is not a secret. `sss.bas:44` `$EMBED`s `assets/.env`, and `.github/workflows/build.yml:82-83` writes `DB_KEY` into every CI build, release builds included. Running `strings` on the binary recovers it.
- `server/src/index.ts:11,109`: `MAX_ROWS = 1000` applies to `/scores` too, so one request can insert 1000 leaderboard rows.
- `server/src/index.ts:129`: `score` accepts any non-negative safe integer (up to 9,007,199,254,740,991), and `wave` likewise.
- `server/src/index.ts:26`: `player_name` is any string of up to 32 characters, with no character rules. The game's own callsign rules are stricter (`src/state/usernamelogic.bas`).
- No rate limiting exists anywhere: `server/wrangler.toml` has no rate-limit binding, and the Worker has no per-IP check.
- There's no moderation path: no delete route, and no documented `wrangler d1 execute` procedure.
- The leaderboard is shown in game, on the title's LEADERBOARD screen (`src/state/leaderboard.bas:40`) and as the game-over rank (`src/state/gameover.bas:145`).

**Impact**
- One `curl` can put 1000 rows of score 9e15 with any names on every player's leaderboard.
- A loop can burn the free plan's 100,000 rows written per day (README:211). Telemetry and score posts then fail for everyone until 00:00 UTC.
- `docs/DESIGN.md` sets the v0.1 bar as "a real, whole experience the first time someone outside that circle sees it". A defaced board on day one misses that bar.

**Recommendation: fix before v0.1.** All of this is Worker-side, small and testable with the existing Vitest suite:
- `/scores` takes exactly one row.
- `score` gets a plausible ceiling and `wave` a range.
- `player_name` must match the callsign charset the game allows.
- Per-IP rate limiting on both POST routes, using the Workers Rate Limiting binding.
- A short README moderation section (how to find and delete rows).
- README says plainly that `DB_KEY` is a client identifier, not a secret.

Accept that a determined player can still submit a fake-but-plausible score. Server-side score validation would need replays, which is out of scope.

## Medium

### 2. Settings and telemetry write to the launch folder with no error handling

**Evidence**
- `src/sys/settings.bas:6` opens `_STARTDIR$ + "/sss_settings.ini"` For Output.
- `src/sys/telemetry.bas:63-64,73` creates `sss_telemetry.csv`, then reopens and closes it on every `TELEM_Row`, which runs on every enemy kill (`TELEM_EnemyKilled`, `telemetry.bas:98-101`).
- The only `ON ERROR` in the game is the `/dev/tty` probe (`sss.bas:75`), and its comment (`sss.bas:67-70`) says unhandled file errors pop error dialogs.

**Impact**
- Launch from a folder the user can't write to and the game raises a runtime-error dialog on the first settings save or telemetry row. During combat that repeats on every kill. Examples: a shared install dir, Program Files on Windows, or a shell whose cwd is `/`.
- Settings, key bindings and the callsign are tied to the launch folder. Starting the game from somewhere else "forgets" them.
- A file open/append/close per kill is avoidable I/O in the frame loop. Antivirus scanning on Windows can turn it into hitches. (Not measured.)

**Recommendation**
- **Fix before v0.1:** probe the launch folder once at startup, the same way the `/dev/tty` probe works. If it can't be written, turn off settings saves and the local CSV for the session, with a `DBG_Print`.
- **v0.2+:** move settings to a per-user config dir (`$XDG_CONFIG_HOME`, `%APPDATA%`, `~/Library/Application Support`) and buffer CSV rows, flushing at session end.

### 3. The release pipeline has never run, and `release` doesn't wait for every check

**Evidence**
- `gh release list` is empty and `git tag` has no tags, so the tag-only paths in `.github/workflows/build.yml` have never executed. These are the `SSS_RELEASE` build (`:84`), the tag-only release smoke test (`:87-90`), the release asset staging (`:120-130`) and the `release` job (`:340-362`).
- `release` `needs: [build, release-smoke]` (`:341`). It doesn't need `render`, `server`, or the `gate` job (`:323-338`), so a tag can publish binaries while render tests are red.
- `gh release create` (`:359`) has no `--prerelease`, so a rehearsal tag such as `v0.1.0-rc1` would publish a normal "latest" release.

**Impact:** tagging v0.1.0 is the first time roughly 40 lines of workflow run. A failure there is recoverable (delete the tag, fix, re-tag), but it's avoidable, and the gating gap could ship a binary that fails render tests.

**Recommendation: fix before v0.1.**
- `release` needs `gate`.
- Pass `--prerelease` when the tag contains `-`.
- Rehearse once with a `v0.1.0-rc1` tag before the real one.

### 4. Docs disagree with the code in places that cost newcomers time

`CONTEXT.md` is corrected in this PR (see "Doc edits in this PR"). What remains:

**`CLAUDE.md`**
- "All `Dim` inside Subs are module-scope in QB64-PE; variable names must be unique across all Subs" is false.
- 85 local variable names are already reused across different Subs and compile in CI. Some even reuse a name with a different type: `c` is an `Integer` in `src/2d/font.bas:22` and an `E3D_Coord` in `src/3d/scene.bas:70`.
- What is true: a plain `Dim` *outside* any Sub in an included file is module-level and invisible to Subs.
- The rule costs every change a needless global-uniqueness check. `CLAUDE.md` is the owner's file, so this review doesn't edit it.

**`README.md`**
- `:31` says building needs only QB64-PE. `tools/buildqb:17-19` also runs `npm install` and `node tools/emit-spline.js` on every `sss.bas` build, so Node/npm (and network on first build) are required. See #11.
- `:271` says to commit the regenerated spline files. `.gitignore:47-49` says `spline_path_gen.bi` must never be committed. Only `tools/TrailForge/src/math/spline_gen.ts` is tracked.
- Remapping (#266/#273) isn't mentioned anywhere: no Settings > CONTROLS, no pad setup wizard, no pause-dialog **K**. The `:289` pause row lists Y/C/ESC but not K (`src/state/playing.bas:37-39`).
- `:181` talks about "builds released before the switch" to the Worker. No release has ever been published.

**`docs/agents/domain.md:23`** says `src/` "does not exist; source lives as *.bas at repo root". It does exist.

**Recommendation: fix before v0.1** (docs only).

## Medium (v0.2+)

### 7. Tests copy shared state instead of including it

**Evidence** (measured by matching each test's `Dim Shared`/`Const` names against `src/sys/dims.bas`)
- **20 of 28** `.bas` tests copy something.
- In total they hold **295** copies of `dims.bas` variables, **144** copies of its constants, and **81** one-line stub Subs/Functions.
- Heaviest: `death_telem_test` (52 vars), the three sequencer tests `seq_dispatch_test` / `seq_trace_test` / `scene_jump_planet_test` (36 vars, 16 consts, 12 stubs each, nearly identical to each other), `crawl_plan_test` / `crawl_step_test` (36 vars, 17 consts), `telem_creds_test` (25), `dbg_output_test` (19 + 19).
- The copies drift:
  - The sequencer tests declare `boss` as a private `Type BossState` with only `warnTimer` (`tests/seq_dispatch_test.bas:51-53`), not the real `BossObj`.
  - Their `DOCK_Enter` stub hard-codes `gameState = 15` (`:111`), not `GS_DOCK`.
  - The constants header says "must match dims.bas" (`:38`), and nothing checks that it does.
- Including the real files already works. Seven tests include `src/engine3d.bi` + `src/sys/dims.bas` (e.g. `tests/dock_test.bas:31-39`).
- The cost is compile time. In CI those tests build in 9-10 s, against 2-3 s for stub-only tests (Build Linux, run 40745435406). Under the parallel runner that adds roughly 7 s per migrated test to its worker, not to the whole suite.

**Impact:** this is the "update every stub" tax in CLAUDE.md. Worse, tests can pass against a shape of the game state that no longer exists.

**Recommendation: v0.2+.**
- Move the eight heaviest tests to `engine3d.bi` + `dims.bas` and keep only Sub stubs for collaborators.
- Fold the three sequencer tests' shared prelude into one `tests/seq_stubs.bi`.
- Then drop the stub note from `CLAUDE.md` and `CONTEXT.md`.

### 8. Global state is large, and partly owned by single modules

**Evidence**
- `src/sys/dims.bas` has 204 `Dim Shared` lines declaring 220 names.
- Across the program there are 538 `Dim Shared` lines declaring **639** distinct names in 37 files. `dims.bas` holds only about a third: `snd.bas` 38 lines, `music.bas` 38, `speech.bas` 35, `behavior.bas` 28, and so on.
- **35 `dims.bas` variables are used by exactly one module.** Examples:
  - `telemBatch`, `telemSession`, `telemKills`, `telemEscapes`, `telemBossReached` (only `telemetry.bas`)
  - `regenEvery`, `regenDelay`, `regenTick`, `armourMul` (only `upgrades.bas`)
  - `optSel`, `optLfRpt`, `optRtRpt` (only `settings.bas`)
  - `unCursorPos`, `unScrollOff`, `unBlinkN` (only `username.bas`)
  - `dbgMlogPath`, `dbgMlogState`, `dbgMlogSeq`, `dbgGraveWas` (only `debug.bas`)
  - `httpLastResp`, `httpLastHeaders` (only `http.bas`)
  - `camUpWas`, `camDnWas`, `rWas`, `thrusterLight` (only `playing.bas`)
- One dead variable: `empireName` is written in `sss.bas:116` and never read. The `{{the_empire}}` token is expanded through `gametext.txt` instead.
- Some names mislead. `lives` (`dims.bas:177`) is the shield value (`GAME_ResetState` sets `lives = shieldMax`), and `shipLives` is the ship count.
- Constants live in `dims.bas` only because of include order (`dims.bas:87-97`: "used by sequence.bas before wave.bas is included").
- Collision risk: no local `Dim` today reuses a `Dim Shared` name (0 found), and duplicate `Dim Shared` names are compile errors. The rule that actually needs guarding is "local name ≠ shared name", not "unique across all Subs" (see #4).

**Impact**
- Every module can write every variable, so a bug's cause can be anywhere.
- `dims.bas` changes ripple into the test stubs (#7).

**Recommendation: v0.2+.**
- Move single-owner variables into their modules, the pattern newer modules (`upgrades.bas`, `input.bas`, `remaplogic.bas`) already use.
- Delete `empireName`.
- Consider renaming `lives` to `shieldHP`, alongside #7, since the stubs copy it.
- Optionally add a CI grep that fails when a Sub-local `Dim` reuses a shared name.

### 9. Input reaches consumers through three layers

**Evidence**
- **One clean device path.** Keyboard: `E3D_InputUpdate` (`src/3d/input.bas:394-439`). Pad: `E3D_PadRead` → `E3D_PadMap` → `E3D_PadApply` (`:444-496`). Scripts: `ISC_Apply` sets the raw pad state and goes through the same `E3D_PadMap` (`src/sys/inputscript.bas:192-216`). Last-device tracking hangs off both paths (`INP_NoteKeys` / `INP_NotePad`, `input.bas:513-533`). After #256/#266/#273 this part is good.
- **Three layers above it:**
  1. `held()` slots named after keys but meaning actions. `held(E3D_KEY_SPACE)` is "fire", whatever key or button is bound.
  2. Raw letter hotkeys through `KEY_Down%`, outside the binding table: the title console A/C/S/L/Q/N (`src/state/title.bas:54-59`), pause Y/N/C/K (`src/state/pauselogic.bas:32-35`), Settings A (`src/sys/settings.bas:193`), backtick (`src/state/crawl.bas:121`, `src/sys/debug.bas:127`).
  3. Typed text through `KEY_Hit&` (`consentlogic.bas`, `usernamelogic.bas`).
- **Two edge-detection styles:**
  - `KEY_Pressed%`, a previous-frame snapshot (`inputscript.bas:219-226`), used in 12 files.
  - 28 hand-rolled `Dim Shared *Was` flags (e.g. `optUpWas` ... `optAboutWas`, `escWas`, `spaceWas`, `pWas`).
  - `TITLE_ReturnTo` (`src/state/titlenav.bas:106-110`) exists to pre-set two of those flags so ESC doesn't leak between screens. `title.bas:69` pre-sets six more by hand.
- **"Pressed" has two values.** Hardware sets `held()` to `1` (`input.bas:395`, `Abs(_KeyDown(...))`); scripts set `-1` (`inputscript.bas:207`). This is safe today only because no code applies `Not` to a `held()` value. Given the CLAUDE.md `Not` gotcha, it's a trap waiting.

**Impact**
- "Is there one clear path from device to action?" Yes up to `held()`; no after it.
- Every new screen picks an edge-detect style and a key-reading style. ESC-leak bugs (#246) come from the `*Was` style.

**Recommendation: v0.2+.**
- Add action accessors (`INP_Down%(E3D_ACT_FIRE)`, `INP_Pressed%(act)`) over `held()` and migrate screens off the `*Was` flags as they're touched.
- Normalise `held()` to `-1`/`0` in `E3D_InputUpdate` / `E3D_PadApply`.
- Accept the raw letter hotkeys: they're menu mnemonics that the remap deliberately doesn't cover.

### 10. Include order, module boundaries, and the logic/draw split

**Evidence**
- **`sss.bas` includes more than the two manifests.** It includes `version.bas`, `rng.bas` and `dims.bas` directly (`sss.bas:51-55`), and the seven main-loop states (title, intro, gameover, crawl, playing, asteroids, combat) inline after startup code (`sss.bas:126-132`).
- **Module-level code runs at include time, in include order.** `input.bas:98-100` calls `E3D_KeyDefaults` / `E3D_PadDefaults` before `dims.bas`'s initializers run (`engine3d.bi` precedes `dims.bas` at `sss.bas:53-54`). Nothing breaks today, but the startup order is implicit.
- **Pure, tested `*logic.bas` modules exist** for the dock (`docklogic`), pause input (`pauselogic`), consent (`consentlogic`), remap (`remaplogic`), callsign (`usernamelogic`, `textedit`), title return (`titlenav`) and menus (`menunav`).
- **Not split:**
  - `src/sys/settings.bas` holds persistence (`SETTINGS_Load`/`SETTINGS_Save`, `:3-98`) *and* the whole Settings screen's input and drawing (`OPTS_Update`, `:100-299`). It lives in `sys/`.
  - The title command console (`title.bas:51-81`), game over, leaderboard, About, Controls and the crawl browser mix input and drawing.
  - The pause dialog is drawn inside `GS_PLAYING_Update` (`src/state/playing.bas:31-63`).
- **No unit test includes `settings.bas`.** `SETTINGS_Load` parses the player's file, including the bindings handed to `E3D_BindsLoadLine%`.

**Impact**
- The settings parser is the most-used untested code: every launch reads it.
- The rest is covered end to end by the playthrough and render suites, so the remaining cost is mostly readability.

**Recommendation**
- **v0.2+:** split `settings.bas` into `settingslogic.bas` (load/save as functions over a string, unit-tested) and `state/options.bas` (screen).
- **Accept** the other unsplit screens until they next change. Split them when touched, the way #273 did.

### 12. Render hot path allocates per mesh per frame

**Evidence**
- `E3D_GetMeshFacesLit` declares `Dim E3D_worldVerts(1 To 8192) As E3D_Coord` as a local (`src/3d/mesh.bas:307`). That's a 96 KB array allocated and zeroed on every call.
- It runs once per drawn mesh per frame: up to 35 enemies, the boss, 25 asteroids, the player and power-ups (`src/state/combat.bas:123-168`). That's roughly 60 calls, about 6 MB zeroed per frame at worst.
- The largest mesh has 546 vertices (BOSS; `assets/models.e3d` holds 1,762 vertices and 2,853 faces across 13 meshes).
- `scene.bas:13-16` already made the face workspace `Dim Shared` "to avoid stack allocation for large meshes"; this array was missed.
- **Other per-frame costs, all small:**
  - `KEY_FrameBegin` copies the 32,768-slot `held()` every frame (`src/sys/inputscript.bas:219-222`).
  - `E3D_ZBufClear` clears 76,800 cells with nested loops (`src/3d/poly.bas:9-21`).
  - The rasterizer does a per-pixel `PSet` behind a z-test, on top of the painter's sort (`poly.bas:74-76`, `scene.bas:76-85`).
  - The scene silently drops faces past 8192 (`scene.bas:26`).
- **Pools are fixed and recycled:** `MAX_BULLETS` 256, `MAX_EBULLETS` 24, `MAX_ENEMIES` 35, `MAX_ASTEROIDS` 25 (`dims.bas:38-45`). Bullets are drawn as 2D bolts, not meshes (`combat.bas:239-247`). That's fine.

**Impact:** wasted memory bandwidth per frame. Frame time wasn't measured in this review; no one has reported a slowdown.

**Recommendation**
- **v0.2+:** make `E3D_worldVerts` `Dim Shared` (or `Static`), sized to the largest mesh. The render goldens will confirm the output is pixel-identical.
- **Accept** the rest. #272 (de-poly) is the bigger lever if frame time ever matters.

### 13. CI runs twice per PR push; the Windows flake

**Evidence**
- `.github/workflows/build.yml:3-8` triggers on `push` to `feat/**`, `fix/**` and `bug/**` *and* on `pull_request`, with no `concurrency` group.
- In the last 40 runs, 36 are 18 push/pull_request pairs for the same commit.
- Wall time is about 2.5-4 min per run. The test suite itself takes 51 s on Windows, 55 s on Linux and 84 s on macOS (run 40745435406).
- The Windows flake (#270) is still open. Twice in those 40 runs, one twin failed on Build Windows while the other passed: 40739323094 against 40739311553, and 40689071385 against 40689092750.

**Impact**
- Doubled runner minutes, and duplicate red checks on a flake.
- The duplicate push run currently works as a free retry for #270, so removing it first would make the flake more visible.

**Recommendation: v0.2+, after #270.** Run `push` only for `master` and tags, and add `concurrency: { group: ${{ github.workflow }}-${{ github.head_ref || github.ref }}, cancel-in-progress: true }` for PRs. #270 itself needs nothing new; leave it at v0.2+, since it doesn't affect shipped binaries.

### 15. Telemetry loses whole sessions (fold into #274)

**Evidence**
- **Window close loses the session.** Events are POSTed once, at `TELEM_SessionEnd` (`src/sys/telemetry.bas:186-206`). There is no window-close handler (no `_EXIT` anywhere), and title QUIT calls `SYSTEM` directly (`src/state/title.bas:73`). `HTTP_Flush` has no callers (`src/sys/http.bas:193`). So a player who gives up by closing the window sends nothing, and that is the "quit" signal #274 wants.
- **Long sessions lose everything.** The Worker rejects more than 1000 rows (`server/src/index.ts:11,109`), and the client doesn't chunk. A session over 1000 events loses all of them.

### For #1: fix(server): harden POST /scores against floods and fake rows before v0.1

**Labels:** `tier:v0.1` · **Milestone:** v0.1

```markdown
## Problem

## Done when
```

### For #15: comment on #274 (no new issue)

```markdown
More gaps from the v0.1 architecture review (finding 15), to fold into this issue:
- **Window-close quits are never recorded.** Events go out once, in `TELEM_SessionEnd`. There's no `_EXIT` handler, title QUIT calls `SYSTEM` directly, and `HTTP_Flush` has no callers. So "gave up and closed the window", the main quit signal, sends nothing. Handle `_EXIT` (end the session as `exit=quit` with the current state, then `HTTP_Flush` with a short timeout), and flush on title QUIT.
- **Long sessions lose everything.** The Worker rejects batches over 1000 rows and the client doesn't chunk. Send in chunks of at most 1000 (or flush at each stage clear).
- **`ev_time` wraps at midnight.** It's `Int(Timer)`, seconds since midnight. Use seconds since session start, or a full timestamp.
```
